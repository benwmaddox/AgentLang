# Main comparison acceptance (coordinator only)

Freeze this procedure with the main starts and scorer before any comparison
participant. It is not a participant hint or a substitute for executing tests.
The seed-only run has its own frozen scorer and is unaffected by this procedure.

To avoid the seed's manual-transcription discrepancy, dispatch a short frozen
wrapper authorizing the participant to read exactly its assigned frozen prompt
file. The wrapper contains the absolute path and expected SHA-256, and forbids
reading other project or study files except through the assigned broker. Archive
both wrapper and prompt bytes. Do not manually retype the full task/allowlist into
the spawn message. This is a prompt-delivery change disclosed before comparison,
not a claim that the earlier seed used this mechanism.

Record each dimension independently. Overall acceptance requires behavior,
structure, preservation, attached tests, required library qualification (language
arms), and task finalization. Preserve failed dimensions even if others pass.

## Behavior

Run all thirteen frozen scenarios against both public summaries, and against
the actor-selected shared customer-total function. Record that function's actual
name before selecting it for scoring; do not search for whichever of several
unused functions happens to pass. It must be the operation used by both summaries.
Require its signature to be Store and CustomerId to Result of Money or
BusinessError, with no effects. Check exact nominal results, full Customer fields,
seven dashboard counts, and stable error codes. The pure language value contract
and full typed Store round-trip support Store preservation; do not describe a
Money-only return value as a directly observed post-call Store snapshot.

All scorer subprocesses must finish successfully, return the expected response
count and preserve input hashes. A harness failure is not an agent behavioral
failure. Archive its evidence; if scoring changes are necessary after dispatch,
invalidate the affected frozen comparison rather than silently repairing it.

## Shared structure

Review saved source and resolved dependencies after fresh reload:

1. Identify the actual shared customer-total function and its typed support
   callbacks. Save their source and dependency edges.
2. Verify the account summary reaches that operation with the queried customer.
3. Verify the dashboard invokes the same operation for each customer and combines
   the results using checked, error-preserving aggregation.
4. Trace invoice-owner lookup, ownership filtering and payment accumulation.
   These must form one customer aggregation implementation shared by both paths.
   Separate active summary algorithms behind a wrapper do not pass. Record any
   now-unused legacy callbacks separately as residual vocabulary: the current
   broker cannot delete persistent functions (`discard` removes staged changes).
   Their continued presence alone does not fail consolidation of the active call
   paths. An untouched pre-existing optional seed may also remain unused;
   report that as non-reuse rather than requiring its deletion.
5. Verify by source that the submitted summaries do not select special behavior
   for fixture identifiers, amounts or other test-specific markers.

Supporting callbacks, ordinary validation and dashboard-level aggregation are
allowed. Do not equate legitimate separate customer and dashboard sums with
duplicate customer aggregation. Do not demand a particular helper name, number
of functions, syntax shape or exact coordinator implementation.

Record source files/function IDs and call sites supporting each judgment. Mark
uncertain structure as unresolved pending review, not automatically passed based
on a dependency graph alone. This small pilot uses a documented source review,
not a new general-purpose semantic duplicate detector.

## Reuse and preservation

For the retained language arm, compare the selected function's stable ID, source,
signature and revision to the accepted agent-created seed. Distinguish unchanged
reuse, reuse with modification, replacement/reimplementation, and unused seed.
For F#, compare the selected helper with the frozen accepted equivalent. The
reset arm has no retained helper. Reuse is a descriptive outcome, not a hidden
requirement for overall correctness: a correct new shared abstraction can pass.

Compare inherited type/function/test sources with the frozen start. The task
permits changes to the duplicated summary families and new supporting definitions;
other inherited behavior and tests must remain intact. Record every changed,
added and removed definition, including removed duplicate callbacks. Run the
complete attached suite after reload. Verify actual library gates and closure
for reusable language functions; do not infer qualification from test counts.

Require explicit task.commit for language participants and clean host.close with
terminal process evidence. F# requires saved changes and successful local tests.
An omitted workflow step remains a separate recorded failure even if the saved
program is behaviorally correct.

## Pilot stopping rule

Predispatch clarification for the main comparison: run one fresh actor per arm
first. If all three satisfy full acceptance (including shared structure and task
finalization), stop as a ceiling/feasibility result. Otherwise run one additional
fresh replica per arm from the same frozen starts. Report all dimensions, all
attempts and this outcome-dependent replication rule. Do not claim statistical
superiority.

This supersedes the provisional behavior-and-preservation-only stopping rule in
plan.md for the main comparison, before any main participant is dispatched. Both
initial summaries are already behaviorally correct: a no-op could otherwise
trigger a misleading ceiling conclusion without completing the refactor. The
published seed plan and seed scoring are unchanged. The final main freeze must
record this clarification explicitly.
