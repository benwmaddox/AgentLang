Status: preparation; no participant outcome. Freeze inputs and accept controls
before dispatch. This is separate from the completed public-function study 211.

## Question and scope

Does availability of the two creator-authored renewal functions change the
outcome of a fresh developer implementing the held-out batch task? Run one new
Luna/max participant per condition, using the same neutral task packet, accepted
CLI, broker allowlist, 100-exchange cap and empty external capabilities.

Retained starts from 210's accepted creator project (fingerprint
`390c0ebc697b735a21e5f12efe508b5e192f3d04c1a8947d9174f1835f62edd2`). Reset starts
from the preceding report-163 domain seed. Neither starts with 211's batch code.
Reset is domain-rich, not the PRD's primitives-only flat mode. Each participant
has a fresh context, may inspect its own project and must preserve all inherited
definitions, types, tests and examples. Do not give target names or other trial
results. Do not contact other agents or inspect oracle/evidence directories.
Launch order is recorded before dispatch. Trial 211 is historical context, not
one arm of this pair. No conventional comparison is claimed for this pilot.

## Acceptance

saved copy. Reuse the exact frozen nine batch cases and full-result/error model
from 210. Require all nine to execute and pass, exact complete response count,
CLI exit zero, all inherited and authored tests/examples passing, batch signature matching the packet,

change the actor project. Compare common inherited evidence separately from

Report behavior, publication, preservation and normal broker finalization as
separate endpoints. The overall accepted edit requires all of these. Retained
target discovery and current production call paths are secondary observations,
not correctness requirements. Reset is allowed to solve the task without either
target name. Do not fabricate an eligible-helper record or invoke 210's
