The language and runtime

Flow is a small, strictly typed data-flow language with C-family syntax. It compiles to one verified typed IR. An interpreter runs that IR for tests and development, and an LLVM backend runs it natively for serving. It turned out to be a good target for exact, safe, efficient code. It was a poor place to write code quickly.

What it looks like

A database-reading function from the Campfire port. Effects are declared, every function has documentation, and an attached test follows it:

fn campfire.server.last-room-visited(user: AuthUser, last-room: Option<String>) -> Int {
    effects db.read
    doc "TrackedRoomVisit#last_room_visited: the last_room cookie's room when it is one of
         the user's, else the user's oldest room; 0 when the user has none."
    let cookie-room = match last-room { none => 0; some text => campfire.server.ruby-to-i(text) }
    let remembered = match db.query("SELECT rooms.id FROM rooms INNER JOIN memberships ...
                                     WHERE memberships.user_id = $userId AND rooms.id = $roomId",
                                     [db.int-param(UserId.value(user.id)), db.int-param(cookie-room)]) {
        error failure => 0
        ok rows => match db.first-row(rows) { none => 0; some row => db.int(row, 0) } }
    ...
    if remembered != 0 { remembered } else { oldest }
}

test campfire.server.last-room-visited/fallback {
    let user = authUser.new(id = UserId.new(1), name = "Ann", role = Role.member(), status = AuthUserStatus.active())
    expect campfire.server.last-room-visited(user, option.some<String>("2")) == 1
}

HTML is written as compile-checked templates. The checker rejects a hole in an attribute-name position or an unclosed element:

fn campfire.views.lightbox() -> Html {
    effects none
    html"""    <dialog class="lightbox" aria-label="Image Viewer (Press escape to close)" ...>
  <img src="" class="lightbox__image" data-lightbox-target="zoomedImage" />
  ...
"""
}

Design choices, judged

ChoiceVerdictWhy
One verified IR shared by interpreter and native codeKeepTests run fast in the interpreter and the server runs natively, with no semantic drift. This made byte-exact parity possible.
Declared, enforced effects, plus capabilities granted by the hostKeep"Can this code touch the database or files?" is visible in every signature and enforced. No mainstream web stack enforces this.
Compile-checked HTML templates with typed Html / RichHtmlKeepIt is structurally hard to write XSS. It forced safer designs; one rejected design was <input {value}class=…>. The cost: templates can't leave an element open, so some partials had to be restructured.
Nominal and refined types, exhaustive matchingKeepThese caught real mistakes before commit, in agent studies and in the port.
A mandatory attached test for every committed functionMixedIt kept the codebase continuously exercised and made changes checkable. It did not certify correct behaviour. It added friction (one test per word, even trivial ones) and invited tests that echo the implementation.
Full coverage and finite-case qualification for library wordsMixedRigorous, but expensive for agents and still blind to wrong expected values.
Code as a dictionary of words edited through commands, not filesReconsiderIt made changes atomic and inspectable. In the later matched comparisons, agents also needed about 1.7–5× more broker exchanges than F# agents editing files, and the "Campfire as files" build had to bolt a sources file mode onto define.
No lambdas, statically named callbacks onlyReconsiderIt kept effects and types simple, but made ordinary code awkward: list processing, sorting, callbacks carrying context.
Per-request arena memory, owning value stack nativelyMixedIt gives very low, predictable memory (15–48 MB per server) and needs no GC. But rendering uses about 650 KB of arena per message for about 10 KB of HTML, because strings are built by immutable concatenation.
Crypto only from OS libraries (BCrypt, libcrypto, libxcrypt)KeepCorrect policy. Flow composed protocols such as signed IDs, the ActiveStorage verifier and CSRF tokens on top of trusted primitives.

Strengths and weaknesses

Strengths

  • Safety by construction.
    • Effects in types.
    • Templates with no unsafe holes.
    • The database, files and crypto reachable only through narrow host operations, and literal-only SQL enforced at build.
  • Exactness.
    • The port reproduces Rails' bytes, including Ruby's Float#to_s, CRC-32 avatar colours, weak ETags, CGI escaping and Rack form decoding.
    • The language could express every one of those precisely.
  • Efficiency. Native throughput is near Rust's, memory is tiny, and there are no GC pauses.
  • Determinism. The same IR gives the same answers in the interpreter and natively. Tests are isolated through fresh virtual providers.
  • Inspectability. Stable word IDs, revision history, structured error codes, and call-site bindings recorded per source site.

Weaknesses

  • Missing basics.
    • No lambdas or closures.
    • No < or > on strings, no bitwise operators.
    • match can't be a statement, and break must be last in its block.
    • Option handling is verbose.
    • Several builtins have no native lowering (string.trim, list.tail, int.max). Code that passed in the interpreter failed the native build.
  • No ecosystem. For one app, the port hand-wrote:
    • CRC-32, using arithmetic in place of XOR;
    • Base64 byte helpers and URL form encoding;
    • an HTML5 tag tokenizer and an auto-linker;
    • a decimal float parser and civil-date arithmetic;
    • Ruby's to_sentence and truncate.
    There is no ORM, no migrations, no background jobs, no WebSockets and no mailer.
  • Parser and tool limits.
    • A 100,000-token limit per define.
    • Template rules that fight partial markup.
    • Escaping problems in generated sources.
  • Bus factor. The compiler, runtime, native host and standard library are all bespoke, so every gap is the project's to fix.

Example of the cost: CRC-32 without bitwise operators

Campfire picks avatar colours with Ruby's Zlib.crc32. Flow has no XOR, so the port emulates it bit by bit with division and remainder:

// value ^= 0xEDB88320
var poly = 3988292384
var result = 0
var place = 1
var left = value
for k in 0..32 {
    if left % 2 != poly % 2 { result = result + place }
    left = left / 2
    poly = poly / 2
    place = place * 2
}

It is correct and tested against zlib's values, but it is about 40 lines for what is one operator elsewhere. Several hand-written stdlib pieces look like this.

The native memory and concurrency research

From day 4, a second track explored a native runtime built around arenas, an owning value stack and Erlang-style mailboxes. It ran in parallel with the agent studies (reports 103–214).

  • Worked Inline nested values with independent owners, arena rewinds during a handler, and native mailboxes with suspension and real I/O correctness (128, 130, 131, 133).
  • Mixed In the matched mailbox load test (140), native process memory was lower than the F# reference. Native RETURN mode's best short-run point (8,000/s) failed its 30-second confirmation, so no throughput advantage was established. With a 5 ms delay, native and F# qualified at the same rate.
  • Did not qualify In the completion-service diagnostic (214), every overload group failed rejection qualification. No arena policy won.

The track was set aside when the priority moved to native Campfire. The Campfire server ended up with a simpler model: one arena per request per worker, a per-worker store, and no mailboxes. That model performed well (see Campfire port). The more ambitious async-arena design was never validated.

How useful is it?

As a production web stack: not useful

Rails or Django ship features faster. Go, Rust or ASP.NET match or beat the performance with mature ecosystems. Flow's speed over Rails is real, but mainstream compiled stacks already provide it without building a language.

As a research vehicle: valuable, but now finished

A small number of language properties were valuable together, and few mainstream stacks combine them:

  • effects that are visible and enforced;
  • no possible XSS;
  • every function tested;
  • native density.

The most plausible niche is sandboxed, agent-generated or multi-tenant code, where capability control matters more than ecosystem. Most of those properties can be approximated in an existing language with lint rules, typed template libraries and CI gates. That is cheaper to test first (see Lessons).
