Build time and interactivity

For most of the project, building the Campfire server took over ten minutes, and adding one function to a loaded project took 99 seconds. The developer asked for Forth-like interactivity on the final day. Eight pull requests brought adding or replacing a function under a second, made the verified build more than 15× faster, and added a two-part build. The cost was a second, incremental compile path, which is now the project's most intricate code.

Profiling showed no single culprit. It found accumulated per-item work that should have been per-batch, and whole-program work repeated for every operation:

  • Program-level checks were redone for every one of ~500 attached test cases.
  • Commit compiled the same dictionary four times, for proposed, durable, final and final-durable states.
  • Every compile re-lowered every word and attachment from source, even when one word changed.
  • There were quadratic scans: the effective word map was rebuilt once per word in commit selection, and list-append closures ran over the whole batch.
  • Publish re-read and re-hashed every stored object about three times per commit.
  • The interpreter re-checked runtime value limits over the whole stack after every instruction. It did so through lazy sequences, and looked up source sites in an ordered map with structural key comparison.

The live dictionary (the Forth model)

In Forth, a definition is added to a running dictionary, and earlier words keep the code they were compiled against. The final design does the same thing over a verified program:

  • Extend, don't rebuild. If a new state only adds Flow words, the new snapshot reuses the running one and verifies only the new functions. The check is that every other entry is the same object; history is ignored. Earlier test bodies stay bound to the program they were verified in, which the new program contains unchanged.
  • Replace by caller closure. A changed word is recompiled together with everything that can reach it:
    • its transitive callers over the IR call graph (validator calls through generated constructors count);
    • every case that calls one of them;
    • every test-file overlay that can reach one of them.
    The verifier rejects any kept function that still calls a replaced one.
  • Re-stated, not recompiled. When a commit only changes word or type status, the IR is identical, so only the snapshot fingerprint changes. Lowering never reads status or maturity.
  • Guards that force a full compile:
    • An added word whose short name some unqualified call site already requested. Flow resolves unqualified calls by short name, so this could rebind the call.
    • A replaced type validator.
    • A Stack-authored word or case in the closure.
    • A closure larger than a third of the dictionary.

How it is kept honest

With AGENTLANG_INCREMENTAL_CHECK=1, every incremental snapshot is also compiled from scratch and compared. The comparison covers:

  • functions, types, generated targets, the source map and coverage;
  • every test, expectation and example body;
  • stored call bindings;
  • whether any body bound to an earlier program could still reach a changed function, which IR comparison alone cannot see.

Every suite was run in both modes before each merge. On the final runs, 311 incremental snapshots in Flow.Runtime and 61 across the FlowHttp and Campfire suites all matched a full compile. New test groups exercise adding, replacing, test-file overlays, the shadowing fallback and reopening a project.

A real bug it surfaced

A test was attached to one word but called a caller of a replaced word. Replacing that word did not run the test, and the full-compile path had the same gap. The commit gate ran only the tests of words whose bodies call the change. It now also runs the tests of every owner with a case whose compiled body reaches the change. That fits "all tests run against all code". It is also a behaviour change: some replacements now run more tests.

Two-part build

scripts/Build-CampfireFlowServer.ps1 -TwoPart runs in two parts.

  • Part 1 defines but doesn't commit, so it runs no tests, then compiles at O0. The code is still parsed, type-checked and IR-verified. The output is marked UNVERIFIED.txt.
  • Part 2 is the normal verified build: commit, every attached test, then O2. A failing test fails part 2.

The FlowHttp tests build an app unverified and run the same parity and protocol checks against it.

Assessment

Good

  • The goal was met. Defining, committing and replacing a word all take well under a second, with every relevant test still run.
  • Most gains came from ordinary engineering: caching per batch, removing quadratic scans, and skipping redundant I/O. None of it weakened a check.
  • The differential check made the fast path safe to ship, and found a gap in the original semantics.

Bad

  • It came too late. Most of the project ran on a 5–10 minute loop, which shaped every other result.
  • The incremental path is a second compiler path. The eight PRs added about 2,100 lines in total, most of the incremental path in #3, #4, #5 and #7. Its soundness rests on unenforced invariants: lowering ignores status, unqualified calls resolve by short name, and retained entries keep object identity.
  • The differential check is opt-in through an environment variable, and CI is manual. If an invariant breaks, nothing catches it unless a checked test exercises that case.
  • Identity-based caching is fast but fragile. A refactor that copies objects silently turns the fast path off. It fails slow, not wrong.
