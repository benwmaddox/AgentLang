AgentLang: what a two-week language experiment showed

AgentLang was an experiment in building a small, strictly typed, introspectable programming language for AI coding agents. Its working name for the data-flow syntax was Flow. The goal was to test whether such a language helps agents make more reliable changes. It was then used to port a real Rails application, Campfire. This report closes the experiment: it says plainly what worked, what did not, and what a future experiment should do differently.

Verdict: archive. The experiment produced a working language, compiler, interpreter, native backend and a partial but byte-exact port of a real web application. That port runs close to hand-written Rust speed in very little memory.

The central hypothesis was not supported. That hypothesis was that an agent-oriented language with an accumulated, discoverable, typed vocabulary helps fresh AI agents make more reliable changes than a mainstream language. In every matched comparison, conventional F# was equally correct. F# needed 2–4× fewer interactions and shorter sessions. Two of the language's edits failed a preservation requirement that F# met.

The remaining value lies in the techniques the work produced, not in the language itself:

  • oracle-checked porting;
  • independent grading with calibrated wrong controls;
  • a verified intermediate representation shared by every backend;
  • incremental "live dictionary" compilation with differential checking.

Those techniques transfer to mainstream languages at a fraction of the cost.

Good and bad, in brief

What went well

  • Exact porting by oracle. Comparing every page and partial against the running Rails app made "done" objective. The Flow server returns Rails' bytes.
  • Performance and memory. The native server reaches 0.6–0.8× of a hand-written Rust port's throughput, in a fraction of the memory, and far above Rails on the same box.
  • Safety by construction.
    • Declared, enforced effects.
    • Compile-checked HTML templates that can't put a hole in an unsafe position.
    • Database, file and crypto access only through narrow host operations.
    • Crypto primitives only from the operating system.
  • One verified IR for every backend. The interpreter and the native code agree by construction. Tests run in the interpreter; serving is native.
  • Honest research method.
    • Frozen protocols and independent oracles.
    • Calibrated wrong controls.
    • Negative results kept on the record rather than explained away.
  • The final interactivity work. A Forth-style live dictionary, an exact differential check against full compiles, and a two-part build (unverified exe in about 17 s, verified in about 38 s more).

What went badly

  • The main hypothesis failed to show. There was no reliability or cost advantage over F#, and agents worked harder in AgentLang.
  • Gates ≠ correctness. Mandatory tests and coverage admitted wrong behaviour and altered inherited fixtures.
  • Missing basics.
    • No lambdas, no string ordering and no bitwise operators.
    • match can't be a statement.
    • Some builtins pass in the interpreter but fail the native build.
  • No ecosystem. CRC-32, Base64 helpers, form encoding, an HTML tokenizer, an auto-linker and date arithmetic were all hand-written for one app.
  • Slow feedback for most of the project. Builds took 5–10+ minutes until the final day. This shaped how work was done.
  • Growing complexity.
    • Runtime.fs alone is 8,600 lines.
    • The fast incremental path is a second compile path that must be kept equal to the first.
  • Scope drift. The project moved from agent research to an app port, then performance, then build tooling. Each step was reasonable, but the original question stopped being tested after day 8.
