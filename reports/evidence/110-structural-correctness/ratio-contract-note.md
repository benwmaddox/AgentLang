# Checked ratio contract and fixed-factor usability

Read-only design note. No implementation or coverage changes proposed for this slice.

The limitation is real. For every Int64 value, scaling by 9/10 produces a representable Int64 and its denominator is nonzero. Nevertheless the generic primitive returns Result<Int,String>. A Money -> Money authored caller must match that Result to obtain the Int. Current IR MatchResult contains both branches, and the library gate requires complete own branch-outcome coverage. The error arm cannot be reached by legitimate Int64 inputs with those fixed constants, so such a caller cannot satisfy that gate merely by writing more tests. Scalar accessors unwrap nominal values, not Result values; the current primitive catalog offers no trusted total Result unwrap/expect operation that removes this mismatch.

Returning Result<Money,String> directly avoids an authored match in some designs, but does not establish that an Error is reachable. A future rule requiring every Result-returning word to exhibit both outcomes would have the same overbreadth for a fixed safe factor. Result represents possible failure in the general operation's contract, not proof that every caller's input domain permits failure. No weakening of current coverage or new primitive is recommended now.

The generic primitive and general Money wrapper remain useful: arbitrary denominators and numerators have legitimate errors, and their attached tests can exercise both branches. Do not claim this first slice immediately makes a total fixed-discount library straightforward. Existing hand-authored bounded quotient/remainder arithmetic can implement fixed 9/10 without a Result match, but retaining that arithmetic burden is precisely the usability gap.

A narrower future contract can make safe scaling total. Example: validated BasisPoints backed by Int with values 0..10000, denominator fixed at 10000; scaling any signed Int64 amount by such a factor never leaves Int64. Separate potentially failing construction of BasisPoints from total application Money x BasisPoints -> Money. A validated unit ratio with denominator nonzero and absolute numerator <= absolute denominator generalizes this, but makes construction/representation more complex; start with bounded basis points if the business use case warrants it.

A nominal validator alone currently does not let the compiler eliminate a generic Result error branch. Implementing the total contract later needs an explicit trusted operation, checked constructor/application interface, or compiler-verifiable refinement proof; it cannot be advertised as already supported merely by declaring a nominal type. Any future finite-outcome gate should respect the declared operation/domain and proven reachable outcomes, rather than treating the syntactic Result type as a promise that both outcomes exist for every constrained caller. The total operation can retain ordinary coverage requirements with no impossible error branch.

Evidence basis: generic result.ok/result.error construction and MatchResult semantics in Compiler/IrInterpreter; primitive catalog has no general Result extraction; AuthoringHelp states complete own branch-outcome coverage for library qualification. This note establishes a contract-design limitation, not a runtime arithmetic defect or efficacy result.
