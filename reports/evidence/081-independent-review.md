**Genuine R01 frozen-verifier failure:** I compared the preserved `runs/R01/acceptance.json`, `prelaunch.json`, and `starting-state.json` with the verifier source at SHA-256 `F58C14AFAD7FB4D774A47861AE3B975DC5F5A3BB48B0386329FDC10320576181`. Several failures are genuine writer/reader schema mismatches. Prepare writes `starting-state.baseline.path` as an absolute repository path, while `Validate-StartingState` accepts only the relative spelling at line 661; the accompanying manifest path is correctly repo-relative. Freeze writes `prelaunch.startingProjectPath` with `Get-RepoPath` at line 1139, so it is intentionally repo-relative, while Verify requires it to be fully qualified at line 263. Verify should resolve each recorded path under the repository, require the exact expected canonical target and containment, and compare resolved paths; it should retain the arm, baseline manifest, and inventory checks. The failed invocation also supplied a relative `StartingProjectPath`; root identified and will correct that caller input, but that does not resolve the separate relative path stored by Freeze.

The model and numeric protocol settings in the pin match the global host contract: model `gpt-6-luna`, `max`, V2, 100 exchanges, 262144 request bytes, 524288 response bytes, null inspection limit, disabled inspection budget, and the expected classifier. `ConvertFrom-Json -AsHashtable` converts the ISO `clockValue` JSON string into `System.DateTime`; Verify then stringifies it and compares it with the original ISO literal at line 302, causing the combined model/limits check to fail despite matching serialized values. The check must preserve and compare the exact JSON string (and apply the same representation consistently to pin and global host data), while keeping the strict protocol-value assertions. Separately, I emulated the existing acceptance/preflight serialization in memory using the saved pin: parsed `prelaunch.data` compact JSON compares equal to the separately parsed pin. Both `clockValue` and `preparedAtUtc` are auto-coerced on both sides; the latter's original `+00:00` spelling normalizes to local `-04:00`, but the current preflight comparison normalizes both sides identically. Reading the clock as a raw JSON string for the strict assertion while leaving the pin object used in acceptance serialization unchanged preserves that binding in this fixture check.

The actual prepared and pinned starting-project and actor rows each contain 12 files, and all four inventory hashes equal `e780f23d85487cb4b8d5bf8365104c98f32ed19575f80e0437489f7b35f32391`. The frozen-start check reports the correct 12-file tree hash but fails because its state wrapper is null. The actor check's `files=1` and null hash are also cascades, not evidence of a one-file actor: `Validate-StartingState` first throws `The property 'Count' cannot be found on this object`, leaving `$startingStateMetadata` null; `Validate-FrozenPin` then reads project/actor/runtime fields from that null wrapper. The verifier should identify and fix the Count access with explicit array handling, and should stop or mark dependent frozen checks unavailable when starting-state validation fails, rather than dereferencing absent metadata.
