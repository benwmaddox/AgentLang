# Efficacy review notes through report 149

Scope: product goals in docs/PRD.md and priorities in docs/ROADMAP.md, with evidence from reports 101, 125, and 140–149. This review does not use report150 or any live-participant material; merge that study only after its report and scoring are final.

## Supported findings

- **Reuse and safe publication are feasible in both environments, but no comparative reliability advantage is established.** In [report 125](../../125-matched-pair-repair.md), all six agents pass 12/12 independent scenarios; retained AgentLang and F# agents both reuse their existing helper, and all six suites catch the two planned regressions. One retained AgentLang agent nevertheless omits task.commit, so behavioral success and task completion remain separate outcomes. In [report 141](../../141-paid-invoice-maintenance.md), all four agents pass the independent behavior checks and preserve the shared structure. Its strict “new tests” criterion splits 0/2 AgentLang and 1/2 F#, although inherited tests plus independent scoring pass; the report itself identifies that criterion as unnecessarily prescriptive.
- **Coverage and mutation checks do not establish domain correctness.** In [report 143](../../143-subscription-overlap-comparison.md), one AgentLang submission passes its suite, full declared library coverage, and the inclusive-boundary mutation check, yet misses the empty occupied-interval rule (18/19); the other AgentLang and both F# submissions pass 19/19. This is evidence that relational business conditions need independent expectations, not a causal F# advantage. [Report 142](../../142-library-dependency-qualification.md) separately demonstrates enforceable authored-dependency qualification and one guided helper-test addition that catches a controlled mutation; it is local contract/adoption evidence, not a matched application-reliability result.
- **A compact core can express a useful invariant, but later reuse is not automatic.** [Report 144](../../144-nonempty-interval-prototype.md) expresses validated nonempty intervals using existing records, Option, and library functions, adds no runtime primitive, and passes a bounded 125-case grid in both AgentLang and F#. It does not integrate the abstraction with Instant/subscriptions or show agent adoption. In [report 145](../../145-rental-vocabulary-reuse.md), all four agents pass 17/17, but neither retained agent calls the interval helper; both environments use direct clipping arithmetic. That helper supplies construction and overlap, not intersection length, so non-use is not evidence that retention generally hurts.
- **Discoverability was a concrete obstacle, then received one bounded correction.** [Report 147](../../147-agent-authored-batch-reuse.md) found a mismatch between the advertised Stack fold syntax and the supported Flow/2 receiver form; both AgentLang participants abandoned after failed discovery, and they exchanged information, so their runs are not independent. The F# retained submission also duplicates instead of reusing its helper. [Report 148](../../148-flow-list-discovery.md) fixes the descriptor/help and one fresh AgentLang participant passes 18/18, but after initially calling the retained query, the final implementation duplicates its calculation when a later error branch is uncovered. [Report 146](../../146-conventional-project-discovery.md) also gives the F# broker an initial project/schema inspection path, so historical interaction counts should not be compared as if tools were matched.
- **Validated inputs appear to ease composition under strict library gates.** In [report 149](../../149-validated-window-reuse.md), both fresh agents pass 18/18 and reuse the coordinator-prepared validated-window API. This supports that API shape, not an AgentLang advantage or unaided abstraction discovery. AgentLang records 21 broker exchanges and F# 11, but these interfaces differ, the samples are one per language, and there is no provider-token accounting; do not infer a cost or F# win from those counts. Across reports, keep each task’s denominators and outcomes separate.
- **Runtime results are separate from agent efficacy.** [Report 140](../../140-matched-mailbox-load.md) finds much lower native process memory in its fixture and comparable matched 500/s, 5 ms throughput for 16-slot RETURN/KEEP and F#. The native no-delay 8,000/s short point fails its 30-second confirmation; four-slot KEEP is capacity-limited. This supports keeping both arena policies available, not a general throughput claim, memory-policy decision, or agent-reliability finding. The specialized typed-mailbox/dataflow versus full-actor model remains undecided.

## Risks and unresolved questions

The main reliability risks evidenced here are (1) discoverability failures that make implemented operations appear unavailable (reports 147–148); (2) strict branch coverage interacting poorly with early validation and reusable Result APIs, potentially encouraging duplication (report 148); and (3) tests that satisfy declared branches/finite values while omitting a relationship among domain fields (report 143). Preserve coverage gates, but pair them with independent boundary/property expectations and separate test adequacy from literal test-count requirements. The validated-window result in report 149 suggests a domain API can remove redundant error states while preserving those gates.

The open hypothesis remains whether accumulated, discoverable vocabulary improves the reliability of subsequent multi-function changes over an equally capable typed repository, especially when edits can create collateral regressions. This matches [report 101](../../101-approach-efficacy-review.md): inspectable project knowledge is the strongest demonstrated value, while comparative reliability remains unproven; its proposed direction is a targeted planted-defect repair with unrelated-behavior checks, not another clean task with universal success. Reports 141–149 do not answer that causally: samples are small, tasks and protocols differ, report147 is contaminated for independence, and several abstractions were coordinator-prepared. No controlled-context or authoritative token evidence is available. Report145’s equal success and report149’s reuse are feasibility observations, not retention effects.

## Next priorities

1. **Close the already-running shared-rule evaluation before scheduling another efficacy microtrial.** Use its finalized independent behavior, preservation, reuse, regression, and workflow outcomes to decide whether one new reliability study is warranted. If it finds no novel failure mode, pause easy task variants rather than accumulate more feasibility wins.
2. **Address the demonstrated product gap in domain representation.** Extend the validated nonempty-interval idea to subscription occupancy, representing cancellation-at-start as absence of an occupied period and nonempty occupancy as a validated value. Route the public overlap decision through that model; test empty, adjacency, clipping, and precedence against an independent occupancy oracle. Keep library coverage and authored-dependency qualification intact. This is a focused structural-correctness improvement based on reports 143–144, not a claim that the type alone ensures correct policy.
3. **Continue the approved native conformance work as a secondary, separate track.** Preserve both KEEP/RETURN choices while validating semantics and investigating the measured scheduling instability; do not expand into a general actor framework or claim runtime results improve coding-agent reliability. The PRD makes reliability the primary experiment and cost secondary; report 140 does not settle the mailbox model.

Recommended immediate action: finish and review the current held-out maintenance evaluation, then implement the occupied-period domain slice before launching any further small comparison.
