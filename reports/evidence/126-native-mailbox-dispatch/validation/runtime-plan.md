# Native mailbox runtime implementation evidence

Scope is limited to `src/AgentLang.Llvm/native/mailbox_runtime.h`, `mailbox_runtime.c`, `mailbox_runtime_windows.c`, `mailbox_runtime_test.c`, and the `runtime-*` artifacts in this directory.

The controller binds the configured initialize/begin/resume table indices to exact ABI3 signatures in one module descriptor, enforces canonical `Int`/`Bool`/`Unit` IDs 0/1/2, and calls the module function pointers directly. It validates all module entries but permits an unrelated zero-output entry only when its output type pointer is null; the three selected controller roles retain strict input/output counts and IDs.

Caller-supplied storage contains fixed mailbox slots, two retained banks and root arrays per mailbox, one scratch arena and one shared workspace. Requirements and stats count each 48-byte arena descriptor in its scratch or retained category; root arrays and control metadata remain in controller backing. The four reported requirement categories reconcile exactly to `storage_bytes`.

Each handler attempt preflights two fresh, distinct, nonzero `uint32_t` generations before changing scratch or staging storage. Generation exhaustion rejects before the handler and leaves active state and pending completion intact. Successful begin/resume swaps the staging bank into active state and poisons/clears the retired bank. Failed handlers leave active state and tokens unchanged and reset/poison scratch, workspace and staging. A runtime-local lease guard rejects reentrant calls to another mailbox while the one shared scratch/workspace is in use.

All caller-supplied API buffers are validated for address-span overflow, overlap with the complete caller-supplied runtime storage, and pairwise overlap before any output reset/write or handler call. Output buffers that overlap module metadata are rejected through the existing descriptor-span helper, including stats outputs after disposal. These checks cover initialize/begin/resume inputs and outputs, stats, and state views. As with the C ABI generally, callers must still pass readable/writable addresses; the runtime does not probe arbitrary pointers.

On Windows, each stateful API obtains its owner identity with `GetCurrentThreadId`; runtime instance IDs come from a checked monotonic `InterlockedCompareExchange64` counter. Tokens contain an opaque runtime instance ID, sequence and mailbox identity. Copies alias the same completion. The sequence does not wrap; only the most recently completed identity is retained. Keep the module loaded through the final API call, including post-disposal stats reads; storage remains caller-owned. The `uint32_t` arena handle generation namespace bounds a runtime to 2,147,483,647 natural handler attempts before safe exhaustion. This slice adds no queue, real I/O, callbacks, or allocation per turn.

## Validation

The direct C unit suite was freshly built with clang for Windows x64 using strict warnings, then run at `-O0` and `-O2`. Each run emitted 69 named JSONL checks and a passing summary. Cases include invalid module/storage, unused zero-output metadata acceptance, busy and reentrant admission, buffer alias rejection (including post-disposal stats), cross-runtime/wrong-owner/stale/duplicate tokens, token/generation exhaustion, foreign thread and post-disposal. The suite also checks failure atomicity, both-bank backing accounting, retained capacity limits, arena-generation reuse, poisoned scratch/workspace/staging, zero outstanding leases, and idempotent cleanup.

The UBSan-trap build used the repository's existing O1 trap recipe and passed all 69 checks. `clang-format --dry-run --Werror` passed for the four assigned native files. Strict production object builds for both runtime C sources passed without `AL_MAILBOX_RUNTIME_TESTING`, and a C++17 header-only syntax check passed without test hooks. See `runtime-results.json` for exact arguments, tool paths, check counts/categories and source/binary hashes; `runtime-O0.jsonl`, `runtime-O2.jsonl` and `runtime-ubsan-trap.jsonl` are the full outputs.
