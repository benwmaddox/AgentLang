## Existing library fixtures with adequate visible-domain coverage

The business integration test stages six business-*.agent files, commits all 53 authored words with library maturity, then reloads them through a fresh Engine ([Business.Transitions Program.fs](../../tests/AgentLang.Business.Transitions.Tests/Program.fs#L1064), commit/reload L1092-L1143).

- Bool-returning functions have direct true and false examples: business.id-valid?, business.email-valid?, business.instant-valid?, subscription.status-valid?, invoice.status-valid?, and money.nonnegative? ([business-values.agent](../../examples/business-values.agent#L10), tests L307-L362 and L591-L600). These are useful branchless Bool-return positives. The joined business source has no Bool or enum parameters, so it does not exercise finite input coverage.
- Each store.customer/product/subscription/invoice/payment Option return has both a no-match and match test ([business-store.agent](../../examples/business-store.agent#L126), paired tests L499-L662).
- The inspected Result-returning parsers, constructors, arithmetic, invoice, subscription, payment, and email operations observe both success and error alternatives. I found no obvious one-sided Result/Option return fixture in this scan.
- No checked example returns Option<Bool>. The Acceptance Option/Result library tests consume Option<Int> or Result<Int,String> and return Int ([Acceptance Program.fs](../../tests/AgentLang.Acceptance/Program.fs#L2145)); they test branches, not finite Option/Result return values.

## Fixture acceptance points

- Preserve existing assertions; add meaningful cases for missing values rather than weakening the gate.
- Record finite inputs at each tested function invocation and parameter position. Expectations and unrelated callers cannot substitute.
- Enumerate every Option<Bool> return value: none, some(false), some(true).
- Keep contracts whose declared finite values cannot be produced out of library maturity, or narrow/rewrite them so every declared value is meaningful.
