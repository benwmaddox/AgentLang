# 267 — Campfire out of the compiler; the page is rendered by Flow

Status: compiler, runtime-boundary and Campfire app milestone (views plan
step 3). The compiler no longer contains any Campfire knowledge. Both Campfire
hosts, native C and .NET, now send a body rendered by Flow templates. The
native throughput numbers from this report on therefore measure markup
generated by the language.

## User direction

- "Campfire test should be an app using this language, not built into the
  compiler."
- Apples-to-apples is the goal: report the throughput cost of rendering in the
  language honestly.

## General app-declared host boundary

- **`OwningNativeHostProfile` is now `AppHost of OwningAppHostManifest`.** The
  application supplies the manifest, loaded with `OwningAppHostManifest.Load`,
  which describes:
  - the entry word and its boundary types;
  - the adapter symbol;
  - the app-owned ABI header and adapter file names;
  - the output limit;
  - the operations, each with an app-chosen stable tag, name, types and
    effects.
- **The compiler checks the boundary generically:**
  - the manifest is well formed: distinct names, distinct nonzero tags;
  - each declared operation matches the verified program's host contract;
  - every reachable host call is in the manifest, with matching types and
    effects;
  - program effects are a subset of the operations' declared effects;
  - the entry is a direct shim to the declared entry word.
- **Removed from `OwningStackAot.fs`:**
  - the room-find and room-read profile cases;
  - the nine-operation table;
  - the Campfire record, scalar and enum shape tables (`requireRecord`,
    `requireEnum`, `requireScalar`);
  - the pinned body of Campfire's `utc-instant.valid?` validator;
  - the reachable-closure equality check;
  - the embedded ABI headers;
  - the Campfire adapter symbols;
  - the `%AlCampfireRoomReadInput` alloca special case, now the generic
    `%AlOwningHostInput`.

  Also removed: an unused room-find helper in `LlvmToolchain.fs` and both
  `campfire_*_abi.h` embedded resources.
- **Safety the type tables gave is still there.** Every adapter output is
  validated against its type index before commit
  (`al_owning_commit_host_output`). That includes refined scalars such as
  `UtcInstant`, whose validator now runs at the boundary instead of having its
  source pinned by the compiler. The adapter remains app code.
- **Campfire supplies its own boundary:**
  `applications/campfire/Native/room-read-host.json` holds the table that used
  to live in the compiler, and `campfire_room_read_host_abi.h` moved next to its
  adapter.
- **Regression oracle.** The room-read module was compiled before and after the
  refactor. The generated LLVM is **identical at O0 and O2** except for the
  renamed input struct type. The room-read verifier passes, 238 assertions, with
  a new check: a manifest missing a reachable operation is rejected before
  emission.
- **Retired: the room-find profile (report 249).** Its single operation is tag 7
  of the room-read profile. Retired with it:
  - its specialized `int64` ABI;
  - `room_sqlite_adapter.c/.h`, `sqlite_subset.h` and `e_sqlite3.def`;
  - `Verify-CampfireNativeSqlite.ps1`;
  - the EntryExport room-find tests.

  None of these were in the gate set. The EntryExport project keeps its pure
  export and room-read entry tests.

## The page body is rendered by Flow

- **`CampfireHttpResponse` gains `body: String`.** Its last field holds the
  rendered markup.
- **`applications/campfire/views.flow`** renders every HTML view:
  - room (report 266);
  - append-message (turbo stream);
  - room-not-found;
  - login page;
  - incompatible-browser.

  `campfire.views.body` dispatches by view; redirects and plain responses carry
  an empty body.
- **The native C renderer** (`campfire_http_renderer.c`) now only parses and
  checks the response contract and sends `body` as-is. Its hand-written markup,
  integer formatting and HTML encoder are deleted (`campfire_html_encoder.c/.h`).
  Status, location, content type and cookie metadata are still decided in app C,
  because they are headers, not HTML.
- **The .NET host renderer** (`ResponseRenderer.fs`) likewise sends `body` and
  no longer builds HTML with .NET's `HtmlEncoder`.
- **Escaping is now Rails-compatible on both hosts.** The C and .NET encoders
  wrote numeric entities (for example `&#x27;`, `&#x2014;`) where Rails writes
  `&#39;` and raw UTF-8.
- **Byte check.** The page the native host now serves (10,041 bytes) equals the
  captured C-rendered page (10,073 bytes) exactly, after normalizing C's
  numeric entities to Rails escaping.
- **Named costs.**
  - The response still carries `room` and `messages`, which the hosts now
    only check for contract consistency; that is extra retained-output copying.
  - The body is copied once more, from the retained output into the HTTP
    response buffer.

## Performance (quick benchmark)

| Server | Page bytes | Req/s | CPU / req | p99 | Peak working set | Peak private |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **AgentLang 267 (Flow-rendered page)** | 10,041 | **8,099** | **0.48 ms** | 2.5 ms | 12.4 MB | 46.3 MB |
| AgentLang 266 (C-rendered page) | 10,073 | 9,008 | 0.43 ms | 2.1 ms | 11.9 MB | 46.2 MB |
| Rust, identity (recorded) | 416,127 | 1,322 | 2.93 ms | 25.9 ms | — | — |
| Rails, identity (recorded) | 463,753 | 19 | 176 ms | 1,108 ms | — | — |

- **The cost of rendering in the language:** −10% req/s and +13% CPU per
  request (about 50 µs), with 0 invalid responses and essentially unchanged
  memory.
- **This is the baseline from now on.** Earlier native numbers measured C-written
  HTML.
- **Not equivalent:** the pages differ, so no speed ratio against Rails or Rust
  is claimed.

## Parity baseline

`scripts/compare_html_structure.py` compares the page the native host now
serves with the Rails capture, using `--mask-deployment`:
- **AgentLang:** 4,894 of 4,896 Rails nodes are missing. The page has no
  `<head>`, no sidebar layout, no rich text, avatars, boosts or composer.
- **Rust port, for comparison:** 325 nodes missing, all CSRF.

This is the number the full-page steps will move.
