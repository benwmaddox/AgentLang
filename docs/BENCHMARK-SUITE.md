# Business benchmark suite: artifact contract

Status: **planned**. The 60-task bank is a specification and proposed golden corpus. Its vectors have not been run through an AgentLang task adapter, a Conventional candidate adapter, or reviewed against executable reference oracles. This document does not claim language/reference equivalence, provider behavior, task completion, or agent-performance improvement.

## Files and trust boundary

`experiments/AgentLang.Benchmarks/task-bank/manifest.json` is the host-side inventory. It declares exactly 20 simple, 20 medium, 10 debugging, and 10 refactoring tasks, each task's retention track, prerequisite IDs, required public operation, snapshot references, and planned status. Each task has three proposed language-neutral cases, for 180 total. Every snapshot hash is null until the real fixture is created and independently hashed. Adapter and acceptance evidence remain pending. A task is not executable until concrete reports for both task adapters and the independent oracle, a reviewed acceptance result, and verified snapshot pins exist.

`task-bank/public/<id>.json` contains only the task prompt and the behavior/API contract the agent must implement. It contains no oracle vectors, acceptance file paths, expected outputs, mutation IDs, or snapshot hashes. `task-bank/acceptance/<id>.json` is host-only and contains proposed language-neutral inputs, expected result/error codes and state projections, vector provenance, and optional structural witness requirements. It must stay outside the agent-readable project root and must never be copied into the prompt or context. The current benchmark runner reads an `oracle` array from its task file and dispatches only to `Runtime.Engine`; it is a smoke-oracle format, not this two-adapter acceptance mechanism.

The separate `experiments/AgentLang.Business` library is the immutable reference for its existing domain operations. The candidate Conventional project must be separate from that oracle. Existing base-operation vectors should be run against the reference before being promoted. Premium, discount, renewal, reminder, and refactoring behaviors are proposed task contracts; they are not behavior already provided by the current F# reference. Their listed outcomes are proposed golden vectors pending host execution and review.

## Suite tracks

Simple and medium tasks use the same task IDs across Flat, Growing, and Conventional comparisons. Flat starts every task from one hash-pinned domain-schema/data-only baseline with no prior agent-authored business words. Growing runs in manifest order and retains accepted changes. Its before-task snapshots are separate pins. A failed task aborts to its before-state; tasks with a failed prerequisite are recorded as skipped, never silently seeded from a gold implementation. Conventional mode receives the equivalent F# candidate project and task contract.

Debugging and refactoring tasks use independent, hash-pinned fixture snapshots. Debug fixtures are generated from a known-good prerequisite state with exactly one documented host-side mutation. Refactor fixtures begin with known-good duplicated logic and attached behavior tests. These task tracks are isolated from the main growth chain; their snapshot recipes and hashes remain pending. They are not described as primitives-only starts.

Refactoring acceptance has two independent parts: behavioral vectors and a structural shared-call witness. AgentLang can eventually supply a deterministic callers/dependencies witness. Conventional F# requires a symbol/call-graph adapter. A passing behavior suite or a matching source substring alone is not proof that a refactor happened.

## Contract and projection conventions

Vectors use JSON-neutral values. Money is signed Int64 minor units, never Float. IDs are distinct nominal categories represented in cases by strings. The F# reference accepts any `Guid.TryParse` form and formats IDs as lower-case `D`; the task bank does not redefine its parser to accept only lower-case canonical strings. Cases should include alternate accepted GUID forms where identifier parsing is under test, then compare normalized output. Email cases use the exact ASCII policy and 254-character limit in `docs/BUSINESS.md`; they do not silently adopt a stricter RFC policy. Date cases represent `DateTimeOffset` values and compare instants after UTC normalization, including equal instants with different offsets. Subscription term, customer kind, and status mappings must be explicit in each adapter. F# quantity is currently Int32 while AgentLang Int is Int64; no boundary case is executable until an adapter either aligns the type or applies and documents an explicit range check.

The current JSON inputs are compact operation-level fragments, not a completed shared typed schema or full reference entities. For example, the proposed `S01` customer fragment contains only `kind`, while the actual F# `Domain.Customer` also requires a nominal ID, validated Email, signed Money balance and creation instant. `Kind` already exists as validated raw text; there is no `ReferenceCustomer` type or customer active Boolean in this reference. The candidate fixtures still need a versioned full schema, deterministic data factories/defaults, and explicit adapter normalization. Missing fields must be filled only by a documented fixture factory; unsupported policy fields must not be silently mapped onto existing entity fields. Existing-operation cross-checks and new-policy vectors remain pending until matched full fixtures and factories are reviewed.

State projections contain only observable domain state. Map-backed F# entities and list-backed AgentLang entities are ordered by normalized ID in the projection; email outbox and sent-email arrays retain FIFO order. Statuses are projected as stable strings. Error comparisons use the reference's stable `DomainError.code`, not message wording. A provider callback is outside claimed parity: language tasks pass explicit `Result` outcomes, whereas the F# reference accepts provider functions. These vectors test the pure outcome transition only.

Vectors tagged `proposed-pending-host-review` are design examples, not evidence. Where a vector depends on an absent operation, missing domain fixture, unsupported structured-value observation, or unchecked primitive, its `executionStatus` is `pending`. The manifest validator proves only inventory, schema, separation, DAG, and promotion-gate shape. It does not prove a vector is correct or executable.

## Known implementation gates

Before any task can be promoted, the suite needs a fixed shared business schema and deterministic initial data; aligned GUID/Email/Instant/Money/quantity semantics; and tested structured observation and acceptance adapters. Typed `list.fold` is now implemented and validated in [milestone 055](../reports/055-early-evaluation-preparation.md), and Runtime offers structured value inspection. Those facilities do not establish full-bank adapter correctness. Date arithmetic/comparison vocabulary, checked Money Result primitives, and complete language/Conventional acceptance adapters remain pending. Do not mark those tasks complete or equivalent until the missing surface and both adapters are tested.

## Verifiable statuses and completion gate

The self-contained task-bank validator checks exact category and vector counts, unique IDs and case IDs, required files and fields, structured inputs and explicit result/error expectations, references, acyclic prerequisites, public/hidden separation, planned status, null snapshot hashes, and pending adapters. It also rejects promotion to executable/verified unless acceptance evidence, all required adapter reports, and every required snapshot have concrete evidence references and SHA-256-shaped pins. This is a shape gate only: it does not read or authenticate referenced evidence files, execute an adapter, review a vector, or prove a hash belongs to a fixture. Passing the validator proves only the artifact contract.

The full section 61 outcome in `docs/REQUIREMENTS.md` remains pending (the artifact bank is partial implementation) until each task has a public prompt, reviewed hidden vectors, executable AgentLang and Conventional adapters, verified snapshots, recorded independent outcomes, and coverage evidence. A full-bank validator pass is not a benchmark run. A benchmark run is not a research result until comparable agents, prompts, retention policies, context budgets, and repetitions are recorded.
